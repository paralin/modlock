---
title: The manifest
description: Every field of mod.json.
---

The manifest is the `mod.json` file at a project's root. It gives the mod's
slug, name, version and language. It can also set the mod's map, movement,
definition changes, settings, metrics and boards, and say where and how its
games play on hyperline.gg. The smallest manifest has just the four required
fields:

```json
{
  "slug": "my-mod",
  "name": "My Mod",
  "version": "0.1.0",
  "language": "LANGUAGE_TYPESCRIPT"
}
```

| Field         | Required | Value                                                                                                                 |
| ------------- | -------- | --------------------------------------------------------------------------------------------------------------------- |
| `slug`        | yes      | Identifier: lowercase letters, digits and hyphens.                                                                    |
| `name`        | yes      | The name players see.                                                                                                 |
| `version`     | yes      | A semantic version: up to 64 letters, digits, `.`, `+` and `-`. Raise it for each publication.                        |
| `language`    | yes      | `LANGUAGE_TYPESCRIPT`, `LANGUAGE_JAVASCRIPT`, `LANGUAGE_LUAU`, `LANGUAGE_PYTHON` or `LANGUAGE_GO`.                    |
| `runtime`     |          | With `RUNTIME_WASM`, `modlock` publishes a TypeScript or JavaScript mod [compiled ahead of time](/languages/typescript#two-runtimes). |
| `map`         |          | The [map](/reference/manifest#map) the mod plays on.                                                                  |
| `movement`    |          | A [movement model](/reference/manifest#movement) that replaces how heroes move.                                       |
| `definitions` |          | [Definition changes](/reference/manifest#definitions) to heroes and abilities.                                        |
| `settings`    |          | [Choices](/reference/manifest#settings) each player makes about the mod.                                              |
| `metrics`     |          | Running [totals](/reference/manifest#metrics) for each player, which the mod adds to.                                 |
| `boards`      |          | [Rankings](/reference/manifest#boards) the mod reports scores to.                                                     |
| `persist`     |          | [Records](/reference/manifest#persist) the mod keeps for each player across sessions.                                 |
| `services`    |          | [Services](/reference/manifest#services) the mod calls, each needed or optional.                                      |
| `freeForAll`  |          | `true` starts the mod in [free-for-all](/guides/toolkit#play-free-for-all).                                           |
| `placement`   |          | [Where](/reference/manifest#placement) the mod's games run on hyperline.gg.                                           |
| `games`       |          | The [games](/reference/manifest#games) players start from hyperline.gg, and how each seats its players.               |

## Map

```json
"map": "hl_parry_ball"
```

`dev` and `play` start the server on the first map in the mod's list that is in
the game's `citadel/maps`. When the mod leaves `map` out, the server starts on
`dl_midtown`, both on your PC and on hyperline.gg.

A mod plays on the stock Deadlock map, `dl_midtown`, or on a map of its own. To
use your own map, name it `hl_<name>` and put the compiled map in
`maps/hl_<name>.vpk`. `build` copies the map into the build, and `publish`
refuses a build that lacks it. The build refuses any other map name, because a
map that is only in your own game's `citadel/maps` would load for you and for no
one else.

## Movement

```json
"movement": { "model": "MODEL_QUAKEWORLD", "scale": 1.25 }
```

| Field   | Value                                                                                                  |
| ------- | ------------------------------------------------------------------------------------------------------ |
| `model` | `MODEL_QUAKEWORLD`: heroes move by QuakeWorld's rules against the Quake collision in `maps/<map>.bsp`. |
| `scale` | Game units per Quake unit.                                                                             |

The server moves the heroes by the model's rules, but each player's game stays
stock. So a player's game predicts its own movement the stock way, and the
server corrects it. Each time a hero lands, the mod's `onLanded` handler gets
the player and anyone they landed on.

## Definitions

```json
"definitions": [
  {
    "file": "FILE_HEROES",
    "entry": "hero_priest",
    "fields": { "CitadelHeroData_t.m_mapStartingStats[EStatsType.EMaxHealth]": 10000 }
  },
  {
    "file": "FILE_BOT_DIFFICULTY",
    "entry": "k_ECitadelBotDifficulty_Hard",
    "fields": { "CBotDifficultyDefinition.low_health": 0, "CBotDifficultyDefinition.low_health_pushed": 0 }
  },
  {
    "file": "FILE_NPC_UNITS",
    "entry": "npc_player_bot_brain",
    "fields": { "CCitadelPlayerBotNPCBrainVData.m_flDisengageFromEnemyToLaneDist": 100000 }
  },
  {
    "file": "FILE_MODIFIERS",
    "entry": "ability_doorman_hotel/pre_teleport",
    "fields": {
      "CModifierVData.m_flDuration": 12,
      "CModifierVData.m_vecScriptValues[EModifierValue.MODIFIER_VALUE_FALL_SPEED_MAX]": 42
    }
  },
  {
    "entry": "gunslinger_rocket_launcher",
    "properties": { "AbilityCooldown": 0.8, "Damage": 120 },
    "fields": {
      "CitadelAbilityVData.m_projectileInfo/ProjectileInfo_t.m_flSpeed": 1250,
      "CitadelAbilityVData.m_mapWeaponInfos[primary]/CCitadelWeaponInfo.m_flBulletSpeed": 4000
    },
    "copyFields": {
      "CAbilityRocketLauncherVData.m_ExplosionParticle": "CitadelAbilityVData.m_skillshotMissParticle"
    },
    "textFields": {
      "CitadelAbilityVData.m_strCastSound": "Hero.Warden.Flask.Throw"
    }
  }
]
```

Each entry changes one stock definition, on the server only. Players' games keep
reading their own stock definitions. So tooltips and parts of the HUD show the
stock values, while play uses the changed ones.

| Field        | Value                                                                                                                                                                                                          |
| ------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `file`       | `FILE_ABILITIES`, the default, for abilities and items; `FILE_HEROES` for heroes; `FILE_BOT_DIFFICULTY` for bot difficulties; `FILE_NPC_UNITS` for units and the bot brain; or `FILE_MODIFIERS` for modifiers. |
| `entry`      | The entry to change, such as `hero_priest`, `gunslinger_rocket_launcher`, `upgrade_colossus/modifier_colossus_active` or `k_ECitadelBotDifficulty_Hard`.                                                       |
| `properties` | Ability properties and their new values, such as `AbilityCooldown`.                                                                                                                                            |
| `fields`     | Float, range-float and modifier-level-float schema fields by `Class.m_field/Class.m_field` path, and their new values.                                                                                         |
| `copyFields` | Copy the field at each value's path over the field at its key's path.                                                                                                                                          |
| `textFields` | Text, symbol, sound event and Panorama image schema fields by `Class.m_field/Class.m_field` path, with `{addon}` replaced by the mod's content addon.                                                          |

A step on a map can end in `[key]` to select one value. For a map keyed by an
enum, such as a hero's starting stats, the key is `[Enum.Value]`. For a map
keyed by name, such as an ability's `m_mapWeaponInfos[primary]`, it is the key's
name. The next step then reads a field inside that value. On a modifier's
`m_vecScriptValues` list, a last step that ends in `[EModifierValue.Value]`
selects one entry.

When you give a single value for a level float or a script value, it fills every
level, and for a range it fills both bounds. The server writes the changes when
it loads the definitions, and again on each new map.

A bot difficulty entry names an `ECitadelBotDifficulty` value. Every bot of that
difficulty reads the changed record, including bots already playing. A bot whose
difficulty does not have a record in the file uses the easy one. A bot retreats to its
base when its health falls below `low_health` percent, or below
`low_health_pushed` percent when it is near an enemy tower. Set both to 0, and
bots fight to the death.

Every bot reads the same `npc_player_bot_brain` unit. When an enemy stands more
than `m_flDisengageFromEnemyToLaneDist` beyond the front of the bot's lane, the
bot gives up the chase and walks back to the lane. Raise that field to let bots
fight away from the lanes.

## Settings

```json
"settings": [
  {
    "key": "layout",
    "label": "HUD layout",
    "kind": "KIND_CHOICE",
    "choices": [
      { "value": "full", "label": "Full" },
      { "value": "compact", "label": "Compact" }
    ],
    "default": "compact"
  },
  { "key": "sounds", "label": "Sounds", "kind": "KIND_SWITCH" },
  { "key": "volume", "label": "Volume", "kind": "KIND_NUMBER", "min": 0, "max": 100, "step": 5 }
]
```

| Kind          | Extra fields         | Value                 | Starts at without `default` |
| ------------- | -------------------- | --------------------- | --------------------------- |
| `KIND_CHOICE` | `choices`            | One choice's `value`  | The first choice            |
| `KIND_SWITCH` |                      | `"true"` or `"false"` | Off                         |
| `KIND_NUMBER` | `min`, `max`, `step` | A number on the step  | `min`                       |

A `key` is up to 64 letters, digits and underscores, and starts with a letter or
an underscore. Every value is stored as text. `modlock build` rejects a setting
that gives players nothing to choose from, such as a choice setting with no
choices, or a number whose `min` is not below its `max`.
[Settings](/guides/data) shows how a mod reads and changes them.

## Metrics

```json
"metrics": [
  { "name": "hud.opened", "kind": "KIND_COUNT", "labels": ["full", "compact"] },
  { "name": "round.best", "kind": "KIND_MAX" }
]
```

| Kind         | Total                        |
| ------------ | ---------------------------- |
| `KIND_COUNT` | How many times it was added. |
| `KIND_SUM`   | The sum of the added values. |
| `KIND_MAX`   | The largest added value.     |

A `name` uses letters, digits, underscores and dots. To keep a separate total
for each value of something, such as one total per HUD layout, list the values
in `labels`. Then pass the label as the third argument of
`player.addMetric(name, value, label)`.

The host keeps the totals in memory. It passes them to its metrics service once,
when the player leaves or the mod stops. When no service takes them, the mod
logs them instead. Bots never get totals.

## Boards

```json
"boards": [
  {
    "name": "aim.score",
    "label": "Best score",
    "unit": "UNIT_NUMBER",
    "order": "ORDER_DESCENDING",
    "keep": "KEEP_BEST",
    "partitions": [
      { "name": "scenario" },
      { "name": "difficulty", "values": ["easy", "medium", "hard"] }
    ],
    "windows": ["WINDOW_ALL_TIME", "WINDOW_WEEK", "WINDOW_DAY"],
    "tier": "TIER_ADMITTED",
    "lowest": "0",
    "highest": "100000"
  }
]
```

| Field               | Value                                                                                                                       |
| ------------------- | --------------------------------------------------------------------------------------------------------------------------- |
| `name`              | The name the code reports to. It uses letters, digits, underscores and dots.                                                |
| `label`             | The board's title on screen.                                                                                                |
| `unit`              | `UNIT_NUMBER` or `UNIT_MILLISECONDS`.                                                                                       |
| `order`             | With `ORDER_DESCENDING`, the board ranks the highest value first. With `ORDER_ASCENDING`, it ranks the lowest first, as for a time.                  |
| `keep`              | The rule that turns a player's scores into their standing, from the table below.                                            |
| `rating`            | `RATING_ELO` or `RATING_GLICKO2`, for a `KEEP_RATING` board.                                                                |
| `partitions`        | Up to four dimensions that split the board into separate rankings. Each dimension may list allowed values.                  |
| `windows`           | `WINDOW_ALL_TIME`, `WINDOW_DAY` and `WINDOW_WEEK`. All time alone by default. Windows follow UTC, and a week starts Monday. |
| `tier`              | The least trusted server whose scores rank: `TIER_HOSTED`, `TIER_ADMITTED` or `TIER_DEDICATED`.                             |
| `lowest`, `highest` | The plausible values. A host holds a score outside them for review.                                                         |
| `version`           | Raise it to start a fresh ranking when the unit, order, keep rule, rating, partitions or team size change.                  |
| `hud`               | With `HUD_END_CARD`, the host shows the player's place after each score.                                                   |
| `teamSize`          | The board ranks teams of two to four players in place of single players, as below. A team board does not keep a rating.                      |

| Keep          | Standing                                           |
| ------------- | -------------------------------------------------- |
| `KEEP_BEST`   | The best value by the board's order.               |
| `KEEP_SUM`    | The sum of the values.                             |
| `KEEP_COUNT`  | How many scores the player reported.               |
| `KEEP_LATEST` | The latest value.                                  |
| `KEEP_RATING` | A rating each `reportMatch` moves from the places. |

When a board has a `teamSize`, it ranks teams in place of single players, such as the
pairs that finish a run together. Each report names the scoring player and their
teammates, so it lists one teammate fewer than the team size. Enroll each
teammate with `bindScorePlayer`, as you do the scoring player.

The same players, in any order, make one team. So a pair keeps one standing,
whichever of them reported, and a player belongs to as many teams as they play
in. Each row of the board lists its team's members. To read a team's own row,
pass the player and their teammates, each still in the game. Under
`modlock dev`, the host refuses a team score that does not name its teammates, and a
single player's score that names any.

```ts
reportScore(enrolled, 'duo.waves', wavesCleared, done, { teammates: [partner] })
```

When your mod reports a score, it gives a value for each partition, and it may
give a `key` for the run. A score sent twice with the same key counts once.
Between equal values, the lower `tiebreak` ranks first. The host's scores
service ranks the scores, decides who may report, and decides how far it trusts
each server. Under `modlock dev`, no such service runs. The host checks each
score against its board and logs it, and the mod logs any score the host does
not accept.

## Services

Name each service the mod calls in `mod.json`. A service is needed unless you
mark it optional. When nobody provides a needed service, the sandbox and the
game host refuse to start the mod, and the refusal names the service. When
nobody provides an optional service, they start the mod anyway, and its calls to
that service fail:

```json
"services": [
  { "name": "example.drills.v1" },
  { "name": "example.ghosts.v1", "optional": true }
]
```

`modlock play` answers a named service from a fixture in the project, both in
the sandbox and in the game. The fixture is `services/<name>.json`, an object
whose keys are the service's methods and whose values are their replies, sent as
JSON. Before the mod starts, `modlock play` logs which provider answers each
named service, a fixture or nobody. In the game, it writes the fixtures to a
file and passes the file's path to the host with `--fixtures`. Each fixture
answers only its own mod.

`modlock play --forward-services <origin>` answers the mod's named services from
the service at that origin, in place of fixtures, in the game only. Each call
the mod starts goes from the host over `--control` to `modlock play`.
`modlock play` posts the call to `<origin>/api/mods/services/call` with the
session that `modlock login` saved, which it reads again for each call, and
hands the answer back to the host. `modlock play` never signs in itself. Without
a saved session for that origin, the call fails, and its error mentions
`modlock login`.

The origin must be https, or http on 127.0.0.1. A forwarded service answers only
the calls started with `callServiceLater`, and at most 8 calls wait on the
origin at once. When `modlock play` exits, the host fails the calls still
waiting.

A service may answer in a later frame, as a service that asks a server across
the network does. `callServiceLater(service, method, payload, done)` returns at
once. Then `done(reply, error, failure)` runs once, in a later frame. It gets
the reply when the service answers. Otherwise it gets the service's refusal, a
timeout, or `unavailable` when nobody provides the service, and then the service
is never asked.

The host waits at most 30 seconds, or the call's own timeout when that is
shorter. When a mod stops or reloads, the host drops the calls the mod still
waits for. A service that answers at once, such as a fixture, answers a started
call the same way, in the next frame, so a mod cannot tell which provider it
has. A host provides a service that answers later with `WasmHost::ProvideLater`.

```json
{ "read": { "key": "slide" }, "save": true }
```

## Persist

```json
"services": [{ "name": "persist" }],
"persist": [
  {
    "name": "stats",
    "writers": "WRITERS_SERVERS",
    "fields": {
      "roundsWon": { "kind": "KIND_COUNT" },
      "longestHide": { "kind": "KIND_MAX" },
      "title": { "kind": "KIND_STRING", "maxBytes": 32 },
      "unlocks": { "kind": "KIND_TAGS" }
    }
  }
]
```

A mod keeps one record of each declared type for each player, and it declares up
to 8 types. It also declares the `persist` service. Each type has up to 32
fields, and a record holds up to 8 KB. Hosts may also bound the manifest's size,
so keep `mod.json` under 256 KiB for the hosts that use that limit.

| Kind          | Holds                                                            | Changes                    |
| ------------- | ---------------------------------------------------------------- | -------------------------- |
| `KIND_COUNT`  | A whole number from zero up.                                     | `add`, `set`               |
| `KIND_NUMBER` | Any number.                                                      | `add`, `max`, `min`, `set` |
| `KIND_MAX`    | The highest number it was given.                                 | `max`                      |
| `KIND_STRING` | Text of up to `maxBytes` bytes: 64 unless declared, at most 256. | `set`                      |
| `KIND_TAGS`   | Up to 256 sorted tags of up to 32 bytes.                         | `insert`, `remove`         |

`writers` is who may change a type's records. With `WRITERS_SERVERS`, the host
takes changes only from a game server it trusts, for values that carry that
trust. With `WRITERS_PLAYERS`, the host also takes the player's own choices.

`persist.get(player, 'stats')` answers `loading` until the record arrives, a
frame or more later. Then it answers `loaded` with the record, or `unavailable`
with the reason. A record that was never written loads empty.

`persist.update(player, 'stats', { roundsWon: { add: 1 }, longestHide: { max: 41 } }, { key: roundId })`
sends up to 32 changes, and the host applies either all of them or none. Changes
merge into the record in place of replacing it, so when two servers update one
player at once, both updates land. Of two `set`s, the later one wins. A `key` of
up to 64 bytes makes a resent update count once, because the host keeps each
record's last 64 keys. An update with an `add` needs a key, and the host refuses
it without one.

When the host answers that an update took too long, the host may still have kept
it. Send it again with the same key, and do not act as if nothing was written.
The host refuses the whole update, and leaves the record unchanged, when a
change breaks its kind's rules, names a field the type does not declare, or
writes a field whose stored value is of another kind than `mod.json` now
declares, or when the record would grow past its bound.

A `Player` kept after its player left cannot reach a record. Its reads answer
`unavailable`, and its updates are refused without being sent, even when another
player has taken the slot. Each request includes the player's connection, and
the host refuses a request whose connection is gone.

`modlock play` keeps the records itself, both in the sandbox and in the game. It
writes one file per player in the project's `.modlock/persist/`, so the records
survive a restart. In the game, `modlock play` learns the player in each slot,
and their connection, as they join, and it refuses a bot's record. When a game
host is too old to send the connection, `modlock play` refuses its every persist
call, so that it never answers for whoever happens to hold the slot.
`modlock play` answers persist itself even with `--forward-services`.

## Placement

```json
"placement": "dedicatedOnly"
```

`placement` is where the mod's games run on hyperline.gg:

| Value              | Effect                                                                                                                                                                                                                |
| ------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `dedicatedAllowed` | The default. A lobby plays on its leader's PC, and the leader of a lobby of two or more may move it to one of Hyperline's game servers. A Draft game always plays on the leader's PC.                                 |
| `dedicatedOnly`    | Every lobby, Draft ones too, plays on Hyperline's game servers, and the mod's code never goes to players' PCs. Choose it when the mod keeps something from players, or needs the server to itself, such as to record. |

Hyperline's administrators can still move the lobbies of one game, or of one
player, without a release.

## Games

```json
"games": [
  {
    "gameId": "mod-prop-hunt",
    "name": "Prop Hunt",
    "seating": "GAME_SEATING_ROTATION"
  }
]
```

Each entry is a game that players start from hyperline.gg. A mod that leaves
`games` out has one game, `mod-<slug>`, named after the mod. When you add
`games` later, keep that ID, so that the game keeps its status and its players'
results. A release with a `games` list retires every game of the mod that the
list no longer names. A release without a `games` list keeps them all.

| Field          | Value                                                                                                       |
| -------------- | ----------------------------------------------------------------------------------------------------------- |
| `gameId`       | The game's stable ID, unique on hyperline.gg. Write `mod-<slug>` for the mod's first game.                  |
| `name`         | The name players see.                                                                                       |
| `description`  | How the game plays, in a few sentences.                                                                     |
| `summary`      | The one line on the game's card.                                                                            |
| `players`      | Who the game is for, such as `"2 or 4"`. Players read it, and the lobby ignores it. The lobby takes its limit from `seating`.      |
| `length`       | How long a match runs, such as `"10 to 15 minutes"`.                                                        |
| `highlights`   | Up to 6 short lines on what makes the game worth playing.                                                   |
| `rules`        | Up to 8 lines on how the game plays, each under 200 characters.                                             |
| `screenshots`  | Up to 8 images for the game's page; see [Page images](#page-images).                                        |
| `match`        | The sides of a team game, such as `{ "amberSize": 3, "sapphireSize": 3 }`. The lobby seats players on them. |
| `seating`      | [Who seats the players](#seating): `GAME_SEATING_LOBBY`, the default, or `GAME_SEATING_ROTATION`.           |
| `experimental` | With `true`, hyperline.gg badges the game as still in progress.                                                                |
| `unlisted`     | With `true`, hyperline.gg leaves the game out of the mod browser, for a game another page starts.                               |

hyperline.gg sets a game's status (Draft, Live, Paused or Retired), its place on
the Play page, and who it credits. So `publish` refuses a `games` entry that
sets any of them. The mod's developers change the status on the mod's page.

### Page images

A game's page on hyperline.gg shows the images in `screenshots`, in order:

| Image     | Where it shows                                                                                  |
| --------- | ----------------------------------------------------------------------------------------------- |
| The first | The cover: the backdrop behind the game's name, summary and Play button at the top of its page. |
| The rest  | The gallery under the page's facts, each with its caption.                                      |

```json
"screenshots": [
  { "url": "media/cover.webp", "caption": "Two fighters on the rim of the pit." },
  { "url": "media/stands.webp", "caption": "The crowd throws from the stands." }
]
```

Each entry has a `url` and a `caption` under 200 characters. The `url` is an
`https` address, a path on hyperline.gg, or a file in the mod's build.
`modlock publish` uploads a file in the build to the site's CDN. A page holds up
to 8 images.

Take each image from the game itself, in 16:9 at 1920 by 1080, as WebP, PNG or
JPEG. Keep each image under 1 MB, the limit for an image uploaded on the mod's
page. A full screenshot in WebP fits well under it. The page crops the cover to
fill its width, and draws it darker behind the text, so keep the cover's subject
near the middle. The game's card on the Play page draws its own artwork, and
shows none of these images.

The mod's developers can also replace the images on the mod's page without a
release. They upload the images there, or paste an `https` address.

### Seating

| `seating`               | Players in a lobby | Who picks teams                                                                       |
| ----------------------- | ------------------ | ------------------------------------------------------------------------------------- |
| `GAME_SEATING_LOBBY`    | Up to 14           | The lobby, on the team seats of `match`. Without a `match`, the players are one list. |
| `GAME_SEATING_ROTATION` | Up to 64           | The mod. The lobby does not have team seats, and the game does not declare a `match`.               |

When a game's mod moves players between teams itself, as hide and seek or a
[rotation mode](/mechanics/rotation) does, give the game
`GAME_SEATING_ROTATION`. The lobby then puts nobody on a team, so the mod's own
team changes stand. A lobby keeps the limit it opened with, so after you publish
a new seating, open a new lobby.

## The built manifest

`modlock build` writes a `mod.json` into `build/`. That copy adds the `entry`
file, and sets the `runtime` that runs the entry. `modlock-host --plugin build`
loads the mod from that file.
