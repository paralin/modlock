---
title: Cut a frame's cost
description: Make fewer game calls, act on changes instead of every frame, and spread work across frames.
---

A common cause of slow frames is work repeated on every frame for every
player. A game call costs more than plain code: the mod encodes the request,
the game does the work, and the mod decodes the reply. Some calls, such as
`giveModifier`, look up game data each time. The skipped-frames line names the
[slowest call](/performance/frame-budget#frames-over-the-allowance), and the
sampled stacks in `modlock play` show which code makes it.

## Act on a change, not every frame

A modifier given again on every frame, to keep it on, costs a call per player
per frame. Hold it instead: `holdModifier` keeps the modifier on the hero with
no expiry and gives it back when the game removes it or the hero returns. Keep
what you last asked for, and call the game only when it changes:

<Samples>

```ts
import type { Player } from 'modlock'

const boost = 'modifier_street_brawl_round_start_zipline_boost'
const boosted = new Set<number>()

function setBoost(player: Player, on: boolean) {
  if (boosted.has(player.slot) === on) return
  if (on) boosted.add(player.slot)
  else boosted.delete(player.slot)
  player.holdModifier(boost, on)
}
```

```luau
local boost = "modifier_street_brawl_round_start_zipline_boost"
local boosted: { [number]: boolean } = {}

local function setBoost(player: modlock.Player, on: boolean)
	if (boosted[player.slot] == true) == on then
		return
	end
	boosted[player.slot] = on or nil
	player:holdModifier(boost, on)
end
```

```python
BOOST = "modifier_street_brawl_round_start_zipline_boost"
boosted: set[int] = set()


def set_boost(player: modlock.Player, on: bool) -> None:
    if (player.slot in boosted) == on:
        return
    if on:
        boosted.add(player.slot)
    else:
        boosted.discard(player.slot)
    player.hold_modifier(BOOST, on)
```

```go
const boost = "modifier_street_brawl_round_start_zipline_boost"

var boosted = map[int32]bool{}

func setBoost(player mod.Player, on bool) {
	if boosted[player.Slot()] == on {
		return
	}
	boosted[player.Slot()] = on
	_ = player.HoldModifier(boost, &on)
}
```

</Samples>

Clear the record for a player who leaves, so a new player in the slot starts
fresh. The same holds for other state the game keeps, such as a hero's
abilities or model: set it once, and again only when something changes it.

## Ask once per frame

Read a value once and pass it to the code that needs it. `player.pawn()` and
`findEntities` each make a call, and `findEntities` searches the world's
entities. In Go, Luau and Python, read each player's pawn once at the top of
the frame; a mode that reads every hero calls `pawns()` instead, which answers
every player's pawn in one call.

The TypeScript library does this for `player.pawn()` itself. Within one event
it reads the first player's pawn with its own call, every other player's with
one `pawns()` call, and answers each later read from those, until the mod makes
a call that may change the game, such as a teleport. A pawn whose state has not
changed since the last read is returned as the same object, so treat a pawn as
read-only. `setPawnCache(false)` turns this off, so every read makes its own
call, to compare the two.

Find the entities a map places, such as zipline nodes, once after the world
loads, and keep the handles. The player list from `players()` is answered from the roster
the host last sent, so it rarely makes a call.

## Stop asking for what fails

A call that fails logs why and returns `false`, or an error in Go. A modifier
the game does not define fails on every try, and each try still pays for the
lookup and adds a log line. Check the result, and stop asking for that
modifier once it fails.

## Spread work across frames

Work that does not need every frame, such as checking who is hiding or
updating a scoreboard, can visit one player per frame. With 12 players each is
checked about five times a second, and no frame pays for all of them:

<Samples>

```ts
import { onFrame, players } from 'modlock'

let next = 0

onFrame(() => {
  const all = players()
  if (all.length === 0) return
  next = (next + 1) % all.length
  checkHiding(all[next].player)
})
```

```luau
local nextIndex = 0

modlock.onFrame(function(frame)
	local all = modlock.players()
	if #all == 0 then
		return
	end
	nextIndex = nextIndex % #all + 1
	checkHiding(all[nextIndex].player)
end)
```

```python
next_index = 0


@modlock.on_frame
def frame(frame: modlock.FrameEvent) -> None:
    global next_index
    everyone = modlock.players()
    if not everyone:
        return
    next_index = (next_index + 1) % len(everyone)
    check_hiding(everyone[next_index].player)
```

```go
var next int

func init() {
	mod.OnFrame(func(frame *mod.FrameEvent) {
		all, _ := mod.Players()
		if len(all) == 0 {
			return
		}
		next = (next + 1) % len(all)
		checkHiding(mod.PlayerOf(all[next].GetPlayer()))
	})
}
```

</Samples>

Use the game clock, such as `frame.timeSeconds`, for anything timed, so the
work keeps its pace when the mod skips a frame.

## Pace long work with a task

Work too long for one frame but short of a round, such as building a list of
hiding spots, can run as a task. A task starts on the next frame, after the
frame handlers, and `pace` returns at once while the frame has time left and
waits for the next frame once it has none. Between two frames the mod's event
has returned, so damage, commands and pings run at once, as they do without a
task. `cancel` ends the task at its next `pace`, and its `finally` blocks run:

<Samples>

```ts
import { task } from 'modlock'

const build = task(async (t) => {
  for (const spot of candidates) {
    score(spot)
    await t.pace()
  }
})
```

```luau
local build = modlock.task(function(t)
	for _, spot in candidates do
		score(spot)
		t:pace()
	end
end)
```

</Samples>

A loop that cannot be a task, such as a frame handler's own slice of work, can
ask `late()` after each unit and stop there. The host gives each mod its share
of the frame only when `MODLOCK_FRAME_BUDGET` names it, or is `all`; with no
budget, `pace` never waits and `late()` is always false, so the task runs to
its end in the frame it starts, as a plain loop would.

## Move computation to a worker

Work that reads no game state, such as decoding a large table or searching it,
can leave the server's tick altogether. A worker is a script of the mod's own,
named `*.worker.ts` in the project's root or `src/`, which the build bundles
into the mod's `data/` directory and the host runs in a second interpreter on
another thread. It may log and read the mod's files and nothing else, answers one
request at a time, and keeps its state between them:

<Samples>

```ts
// table.worker.ts
import { serve } from 'modlock/worker'
import { answer } from './table'

serve(answer)
```

</Samples>

The mod calls it with the same function, and the answer arrives in a later
frame:

<Samples>

```ts
import { worker } from 'modlock'
import { answer } from './table'

const table = worker('table.worker.js', answer)
const spot = await table.call(question)
```

</Samples>

The answer is copied into the mod on the tick, at about 2 ms a megabyte, so
keep large state in the worker and answer with what the mod needs now. A host
runs workers only for the mods `MODLOCK_WORKERS` names, or for all of them with
`all`; for any other mod, `call` runs the function in the mod itself as a task,
so the mod behaves the same and only the tick pays for the work.

## Send less

Each call's request and reply pass through an encoder and a decoder in your
mod, and a mod that makes hundreds of calls a frame spends much of its time
there. In a slow frame's stacks this shows as functions named `encode` and
`decode`. Make fewer calls, as above, and send an interface or a
state update only when it changes, not on every frame.
