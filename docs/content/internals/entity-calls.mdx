---
title: Entity calls
description: What the host does and checks when a mod creates an entity, touches a field, sends an input or deals damage.
---

Each entity call takes an entity by one of its
[four names](/internals/entity-schema#four-names-for-one-entity). Every method
of the typed libraries [generated from the game](/internals/entity-schema) comes
down to the calls on this page, and a mod may also make these calls by hand.

## Creating an entity

```ts
import { create } from 'modlock/entities'

const guardian = create('npc_trooper_boss', {
  team: 3,
  position,
  keys: { rendercolor: 0xff0000ff },
})
guardian?.inputAlpha(128)
guardian?.inputColor(0x00ff00ff)
```

The same call in Go:

```go
boss, err := entity.NpcTrooperBoss.Create(
	&mod.EntityOptions{Team: 3, Position: position},
	&entity.CNPC_TrooperBossKeys{},
)
_, err = entity.CBaseModelEntity(boss).InputAlpha(128)
```

And in Luau:

```luau
local boss: entities.CNPC_TrooperBoss? = entities.create("npc_trooper_boss", { team = 3, position = position })
```

Underneath, each sample makes one `createEntity` call. A mod may also make that
call by hand, with any designer name and untyped key values. The host runs the
call in this order:

1. It checks that the placement is finite.
2. It resolves the designer name's entity class through the game's class
   lookup; an unknown designer name fails here.
3. It refuses any class that derives from `CCitadelBaseAbility` (abilities,
   items, and weapons). Spawning one standalone without an owning hero crashes
   the server when it thinks or is removed, so the host rejects it before
   allocation and directs callers to `giveItem` and `replaceAbility`.
4. It creates the entity, installs its subclass, and applies the spawn key
   values, the position and the facing.
5. It writes the fields in `EntityOptions.fields`. These are fields the game
   reads only while spawning, such as a unit's `m_iInitialTeamNum`. A write
   that fails removes the entity unspawned and fails the call.
6. It spawns the entity and returns its handle.

The host records every entity a mod creates. It removes them when the world
ends, and when the mod stops or reloads. So a mod never leaves entities behind.

### Units and pickups

`spawnNpc` and `createPickup` are built on the same call. `spawnNpc` takes any
unit class the server has, with its subclass as `unit`, and adds what a unit
needs: health, maximum health and a lane. The host writes the lane to the
class's `m_iLane` field before the unit spawns. For a class without that field,
such as `npc_yakuza_gangster`, the call fails with a message that gives the
class. The `Npc` it returns reads, moves, heals and removes the unit.

`createPickup` makes the soul urn or the movement buff, with the designer name
and subclass each needs. The `Pickup` it returns reports whether the pickup
still lies in the world, and removes it.

### Scale

Every entity takes the `SetScale` input, which is `inputSetScale` on
`CBaseEntity`. The input sets the scene node's absolute scale, and the server
rebuilds the entity's physics shape at that scale, so the collision and the
model grow together. Send it once the entity has spawned:

```ts
const ball = create('citadel_hideout_ball', { position })
ball?.inputSetScale(9)
```

The sample sends the input in place of passing the spawn keys `scale` or
`ModelScale`. Those keys set the same scale before the entity spawns. But an
entity whose game data sets its own model scale replaces them while it spawns.

The hideout ball shows both. Its model spans ±7 units, and its game data sets a
model scale of 3, which gives it a radius of 21. With either key, its collision
stayed at 21 units. After `inputSetScale(9)`, a trace meets it at 63 units, and
for every scale from 0.5 to 9, a trace meets it at 7 times the scale. So use the
input for a scale that must hold.

## Fields

A mod reads and writes a field of any live entity by class and name:

```ts
import { readField, writeField } from 'modlock'

const health = readField(pawn.entity, 'CBaseEntity', 'm_iHealth', 'int32')
writeField(pawn.entity, 'CBaseEntity', 'm_iHealth', 'int32', 500)
```

or through a typed class, which supplies the class, name and type:

```ts
import { CCitadelPlayerPawn } from 'modlock/entities'

const hero = new CCitadelPlayerPawn(pawn.entity)
hero.m_iHealth = (hero.m_iHealth ?? 0) + 50
```

The typed `hero.m_iHealth` calls `readField` and `writeField` with the class
that declares the field, `CBaseEntity`, so the two samples make the same calls.

The first time any mod on the server uses a field, the host looks up the field's
offset in the schema, and caches it until the server exits. Before it touches
memory, the host checks that the entity is of the class the call gives, or of a
class that derives from it. So a `writeField` call that passes a trooper's
handle with the class `CCitadelPlayerPawn` fails with a message that gives both
classes, and the host writes nothing. A write marks the field changed, so the
server sends it to the players.

A dotted field name reaches a field inside an embedded structure, such as the
collision group of a model entity's collision property:

```ts
writeField(prop, 'CBaseModelEntity', 'm_Collision.m_CollisionGroup', 'uint8', 2)
writeField(
  prop,
  'CBaseModelEntity',
  'm_Collision.m_collisionAttribute.m_nInteractsExclude',
  'uint64',
  0n,
)
```

In the first call, `m_Collision` holds the collision property, and
`m_CollisionGroup` is a field inside it. Each segment of a path is a field of
the structure that the segment before it holds. The host refuses a path that
goes through a field holding a number, a pointer or a handle.

A field can be a boolean, a signed or unsigned integer of 8 to 64 bits, a 32 or
64-bit float, a vector, an entity handle or a string. Angles are read and
written as vectors. A typed field whose type is another entity class reads as
that class, so `hero.m_hController` is a controller whose own fields a mod can
read.

The host checks the requested type against the type the schema declares for the
field, and refuses a mismatch with a message that gives both types. Each
requested type reads these fields:

- Any number type, a boolean or a handle reads a field that holds a number,
  boolean, enum, handle or boxed number such as `GameTime_t`. The value is cut
  to the requested type's size.
- `vector` reads a `Vector`, `VectorWS` or `QAngle`.
- `string` reads a `CUtlString` or `CUtlSymbolLarge`, and never writes.
- A list call reads a `CUtlVector` or `CNetworkUtlVectorBase` of one of those,
  and a single-value call never reads a list.

A mod cannot read or write a pointer, an embedded structure or any other
container by value. Reach a structure's fields with a dotted name instead.

### The match's state

The match's state is in the game rules: each team's gold, the game state, the
winning team, the Mid Boss count and the pause fields. The game rules are not an
entity. Their proxy entity, `citadel_gamerules`, points to them and sends them
to the players. A mod reads them through the classes `CGameRules` and
`CCitadelGameRules`, with the proxy's handle:

```ts
import { findEntities } from 'modlock'
import { CCitadelGameRules } from 'modlock/entities'

const [proxy] = findEntities('citadel_gamerules')
const rules = new CCitadelGameRules(proxy)
rules.m_nAmberGold = 10000
```

Setting `m_nAmberGold` sends all of the game rules to the players, so the
players already in the match see the change at once. When the game's clients
derive a field from other state, the game may set that field again on its next
update.

A field that holds a list of numbers, handles, booleans, vectors or text, such
as the banned heroes or the neutral camp spawn times, reads as an array. Writing
it replaces the whole array. When the new array is longer than the space the
game allocated, the host grows the game's list. A mod cannot read or write a
list of structures, such as the Mid Boss team states.

```ts
rules.m_vecBannedHeroes = [1, 2, 3]
const times = rules.m_vecNeutralCampNextSpawnTimes // number[]
```

## Inputs

`fireInput(handle, input, value)` sends an entity an input, as a map's output
would. The inputs include `Kill`, `Color`, `Alpha`, `Skin`, `SetScale`,
`StartShake`, `Explode` and the thousand others in `entities.json`. The entity
reads the value as the type the input takes, and does not convert text. `Alpha`
takes an integer, and `Color` takes a color written as `0xRRGGBBAA`. A typed
class sends each input from a method whose parameter has that type:

```ts
const shake = create('env_shake', {
  position,
  keys: { amplitude: 12, frequency: 40, duration: 2, radius: 2000 },
})
shake?.inputStartShake()

const boom = create('env_explosion', {
  position,
  keys: { iMagnitude: 50, iRadiusOverride: 200 },
})
boom?.inputExplode()
```

Each `input` method calls `fireInput` with its input's name, so
`shake?.inputStartShake()` fires `StartShake`. A `fireInput` call with an input
the entity does not have returns `false`, and the host logs the entity's
designer name and the input's name. Only that call fails, so the rest of the
handler runs, and the mod keeps running.

## Damage and deaths

`damage` deals ordinary damage through the engine, and `killEntity` forces a
hero or unit to die. Both take a `victim`, an `attacker`, an `inflictor` and an
optional `ability`. The `inflictor` defaults to the attacker. `damage` also
takes an `amount`.

- Handles encode the entity's generation, so a stale handle fails rather than
  matching a recycled slot. If the attacker has since died or left, the engine
  credits nobody.
- `killEntity` credits the attacker through the game's own damage and reward
  logic. It bypasses resistance and damage modification, and suppresses item
  procs. A living pawn at zero health still goes through its death, and a call
  on a victim already dead succeeds without paying a second reward. Before the
  call, release any immortality your mode gave the victim.
- A call without an attacker causes an environmental death, as `player.kill()`
  does, and nobody gets credit or rewards for it.
- Both calls refuse the world, props and buildings, because clients cannot
  safely process their damage events.

For some deaths, such as a hero knocked out of the play area or into a hazard,
the engine does not credit anyone. To credit such a death, the mod keeps the
handle of the last enemy that hit or pushed the victim. When the victim dies,
the mod passes that handle as `attacker` to `killEntity`. The engine then awards
the kill, the assists and the rewards, so a mod should leave the scoreboard
fields alone.

## What fails, and how

Every entity call fails on its own. It logs the failure, and returns `undefined`
or `false` in TypeScript and Luau, or an error in Go, and the mod keeps running.
These are the failures a mod can meet:

| Message                                       | Cause                                                        |
| --------------------------------------------- | ------------------------------------------------------------ |
| `the server has no entity NAME`               | The designer name is not in this build                       |
| `NAME is an ability, which only a hero holds` | An ability, item or weapon; give it to a hero instead        |
| `NAME crashes the server when created alone`  | One of the entities below; the message says what it needs    |
| `NAME walks no lane`                          | `spawnNpc` was given a lane for a class without `m_iLane`    |
| `NAME has no native identity`                 | The entity was created without a handle the host can address |
| `NAME has no input INPUT`                     | The input is not one the entity accepts                      |
| A class mismatch giving both classes          | A call gave a class the entity does not derive from          |

`createEntity` rejects the 25 designer names below before allocation, and the
generated libraries omit constructors for them. Each depends on state from a
map, game mode, owning hero, or parent ability and crashes the server if
spawned standalone. For example, a bounce pad constructs cleanly, but queries
the ability that placed it to determine its team, crashing the server on the
first hero contact if spawned alone.

| Needs                      | Designer names                                                                                                                                          |
| -------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------- |
| The ability that makes it  | `citadel_bounce_pad`, `citadel_deployable_preview`, `citadel_magician_turret_object`, `citadel_mobile_resupply_object`, `citadel_nano_predatory_statue` |
| An owner                   | `citadel_hideout_prop_base`, `citadel_trigger_capture_zipline`, `npc_familiar_helper`, `npc_shielded_sentry`                                            |
| Its map's game data        | `citadel_herotest_orbspawner`, `citadel_hideout_shootable_target_spawner`, `simple_animating_ai`, `env_laser`, `point_prefab`                           |
| A model or path from a map | `func_precipitation`, `spark_shower`, `path_node`, `path_node_mover`                                                                                    |
| The hideout map            | `npc_neutral_hideout_cat`, `npc_neutral_hideout_rabbit`                                                                                                 |
| A game mode's capture data | `citadel_capture_point`, `citadel_multi_capture_point`                                                                                                  |
| A game mode's cash-in data | `citadel_koth_cashin`                                                                                                                                   |
| A player or bot            | `baseplayerpawn` (spawn a hero), `npc_player_bot_brain` (add a bot)                                                                                     |
| Joined objects             | `physics_npc_solver`                                                                                                                                    |
