title: Building Modlock
description: Build the command line, the host and the libraries from source.

To build Modlock, you need Go, CMake 3.24+ and a C++23 compiler. CMake downloads
[wasi-sdk](https://github.com/WebAssembly/wasi-sdk) to build QuickJS and Luau.

```sh
git submodule update --init --recursive
go mod download github.com/aperturerobotics/protobuf github.com/aperturerobotics/abseil-cpp

jobs=$(( $(getconf _NPROCESSORS_ONLN) / 2 ))
cmake -S . -B build -G Ninja -DCMAKE_BUILD_TYPE=Release
cmake --build build --parallel "$jobs"
ctest --test-dir build --output-on-failure
cmake --install build --prefix "$PWD/build/sdk"
```

Protobuf and abseil take a long time to build, so use half the cores, as shown,
and the machine stays usable while it builds.

The native tests build into two binaries: `modlock_tests` (requires only the
SDK) and `modlock_mod_tests` (runs built example mods, requiring Go and the
mod runtimes). CTest runs each case in its own process. To run a few cases,
select them by name:

```sh
cmake --build build --target modlock_tests
ctest --test-dir build -R 'EntityRules\.'
build/modlock_tests --gtest_filter='EntityRules.*'
```

CMake downloads the [Wasmtime C API](https://docs.wasmtime.dev/c-api/) release
for the target platform. To build offline, pass
`-DMODLOCK_WASMTIME_DIR=<extracted release>`. The install step puts the Wasmtime
library next to `modlock-host`, and the host loads it from there.

- **Windows:** run `scripts/win-build.ps1` from a Visual Studio developer shell.
- **macOS or Linux, targeting Windows:** `scripts/proton-build.sh` cross-builds
  the Windows SDK with Zig.

To build from a source archive without `.git`, pass its commit with
`-DMODLOCK_REVISION=<40-character SHA>`.

After a game update, regenerate the entity and console libraries as
[The entity system](/internals/entity-schema#updating-for-a-new-game-build)
describes.

## Pre-commit hook and scripts

`bun install` installs a pre-commit hook. On each commit, the hook:

- formats the staged files with oxfmt and restages them
- checks the staged TypeScript for commented code paragraphs with
  `scripts/tsstyle.ts`
- lints the staged TypeScript with type-aware oxlint

These scripts run the same tools across the repository:

| Script                       | Does                                                                                                                                                       |
| ---------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `bun run format`             | Formats with oxfmt                                                                                                                                         |
| `bun run lint`               | Lints with oxlint; lint the example mods after `go run ./cmd/modlock build examples/<mod>` installs their typings                                          |
| `bun run typecheck`          | Type checks the TypeScript                                                                                                                                 |
| `bun run test`               | Runs the tests                                                                                                                                             |
| `bun run lint:cc [--fix]`    | Reports or removes unused `#include` directives in C++ sources; reads compile databases from `build/` and `scripts/proton-build.sh`, so build both first |

## Run the command from a clone

Run Modlock from a clone for a fix that is not in a release yet, or to change
Modlock itself. Build the command from the checkout with
[Go](https://go.dev/dl/):

```sh
git clone https://github.com/paralin/modlock.git
cd modlock
go build -o "$(go env GOPATH)/bin/modlock" ./cmd/modlock
```

Build without `-trimpath`, because the command finds the checkout through the
paths compiled into it. The command then builds the TypeScript library in
[`js/`](https://github.com/paralin/modlock/tree/master/js), the renderer and the
preview page from the checkout, so your mods use the checkout's library. A
command built from Modlock source in the Go module cache, as `go install` builds
it, does the same from that source, and caches the result. A release build has
the library built in, and copies it into your user cache the first time it needs
it. After a `git pull`, build the command again.

A command built from source cannot download the host from a release, so set
`MODLOCK_HOST` to a `modlock-host.exe`. The sandbox needs it too, because it
runs the interpreters that come beside the host. For a checkout of a release, or
one close to a release, unpack that release's host:

```sh
curl -LO https://github.com/paralin/modlock/releases/latest/download/modlock-host-windows-x64.zip
unzip modlock-host-windows-x64.zip -d ~/modlock-host
export MODLOCK_HOST=~/modlock-host/modlock-host.exe
modlock new my-mod
cd my-mod
modlock dev
```

On Windows, build `modlock.exe` the same way, and set `$env:MODLOCK_HOST`. When
you change the host itself, the C++ under `src/`, build the host from the same
checkout. `scripts/win-build.ps1` installs it in `build-win/sdk/bin`, and
`scripts/proton-build.sh` installs it in `build-proton/sdk/bin`. Build the host
from the checkout too when the checkout's library is newer than a release,
because a release's host may not have every call that a newer library makes.
